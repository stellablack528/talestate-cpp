## 结论

最大的阻碍是：当前系统把“自由行动的世界模拟”和“固定剧情规则的自然语言入口”混在了一起，又用少量文本记录模拟长期人物和事实。继续增加提示词、行动分支和外围功能，会让它更难理解，却不能自然获得一个持续可信的世界。

现有项目有可复用的规则执行与测试基础，不应因为改用前端或后端就全部丢弃。应保留状态提交、类型化动作、引用校验等思路，重做会话组织、世界实体与物品归属、任务证据和人物记忆。C++、Qt 和 Story Package v1 均不必成为新的硬约束。

Ren’Py 值得作为单人叙事前端做一个小原型。Evennia 在未来确认要做多人持续世界时价值更大；当前不建议同时引入 Evennia、保留完整 C++ 世界状态，再让 Ren’Py 维护另一份状态。

## 1. 已经实测的六个问题

审查探针直接链接当前 `build/storyforge.lib`，使用自带雾港世界；模型回复由固定假 Provider 提供，无真实 API 请求和费用。探针不改变产品源码。

| 问题 | 实际结果 | 判断与影响 |
|---|---|---|
| 空动作仍修改进度 | Agent 返回 `actions: []`，回合从 0 到 1，`state_equal=0` | 与返回的“世界状态没有改变”说法冲突。需明确失败、闲聊、观察何时算一个回合。 |
| 跳时间漏掉每日事件 | 睡眠后当前分钟 480，有尚未发生的第 600 分钟事件；`skip(next)` 失败 | 事件确实存在，却不参与下一事件选择。睡眠与“跳到下一关键时刻”功能未统一。 |
| 承诺无需交付证据就可履行 | 创建“交付不存在的王冠”承诺，背包为空，仍可变为 `fulfilled` | 当前验证的只是人在场和状态合法，不是承诺内容已经完成。若当成任务完成依据，世界可信性会被绕开。 |

## 2. 最影响后续开发的设计阻碍

### 2.1 自由行动缺少合适的世界模型

`StoryPackage` 仍围绕 chapter / scene / node / choice 组织。`AgentAction` 与 `StoryChoice` 的字段几乎相同，运行时经常先把 AgentAction 转成 StoryChoice 执行。通用行动只有有限枚举，其他后果依赖作者预先写好的 action 或 dialogue rule。

这适合“用自然语言选择已有行动”，却不自然支持“把物品放入容器、拿回来、NPC 持有后再转交、基于属性尝试未预写的行为”。`AgentNpc` 只有 ID、名字、位置、对话规则和初始关系，没有统一的持有物、目标、知识和行为状态。

建议先做简单实体模型：实体、位置、物品归属、少量动作前置与效果。任务由实际提交事件驱动。固定剧情图可作为特定世界的玩法，不能继续决定所有世界的结构。

### 2.2 事实、角色知道的事情、玩家看到的叙述没有形成闭环

`state_json()` 会把各 NPC 的 memory、关系及完整变量交给同一个规划/叙述流程；规划上下文还枚举所有场景与 NPC。当前不是“每个角色独立知道不同事情”的知识系统。

`world_lore` 的 facts / rumors / secrets / rules / style 会生成、加载、验证，但常规 Agent 回合没有消费该字段的实现。隐藏秘密不进入普通摘要有价值，但还缺“谁通过什么事件知道了什么”的揭示机制。不能把“不把 secrets 发出去”当成完整的角色知识设计。

建议第一版只区分三类：引擎已确认事件、角色已知信息、自由叙述。涉及奖励、物品、地点和任务完成的文字应由提交结果提供；开放闲聊允许创作，但不能自动成为世界事实。不要现在再造庞大的知识图谱。

### 2.3 长期 NPC 体验的记忆过薄

普通交谈主要保存 `last_discussed_topic`；特殊规则记录少量布尔/字符串。`recent_turns_` 只保留六轮；读档会新建 StoryAgent，清空故事展示和这些临时摘要。

因此背包与位置恢复了，不等于 NPC 能承接之前的闲聊、个人经历和关系变化。这是实际体验风险；本次未用真实模型量化遗忘程度。

建议把简短人物关系记录、必要的对话摘要和最近交互一同保存，按当前人物取用。先服务于同一个 NPC 的连续交流，不先建设复杂检索平台。

### 2.4 物品与任务不是可持续的世界实体

`give` 的实现从玩家背包删除一个物品并执行作者效果，没有通用 NPC 背包或物品所有者。现有世界可以把送礼当作消耗，但无法普遍回答“刚送出的东西现在在哪，能否取回”。

`DynamicFact` 又以字符串 kind/status 混合线索、承诺、求助和计划。`corroborate` 主要检查第二来源与原来源不同且在场，没有验证它为何支持该命题；源码也明确表示这不等于最终真相。履约同样缺完成证据。

建议先完成“交付改变物品归属 → delivered 事件 → 任务完成 → 奖励一次”这一条真实因果链。暂时把普通承诺当作笔记，避免误充任务验证。

### 2.5 强制玩法模板与游戏初衷不匹配

目前生成器会固定选择三个连通地点、三件可收集物和一组证据追问结构，并在生成提示中要求预约和后续计划。这让不同世界容易被压成同一种调查小品。

所有游戏状态又都带有生命、疲劳、生病、睡眠与十年时间范围。时间和生存玩法可以成立，但它们不应是每种校园、恋爱、悬疑或奇幻世界都被迫承担的通用底层。

建议首版围绕一个具体可玩的目标。证据调查、预约、生存和校园日历均按世界需要逐步加入；不是删除后永不支持。

### 2.6 一个会话的流程分散在 UI、Agent 和 runtime

`main.cpp` 约 1,400 个非空行，混合界面、世界生成、文件操作、建角规则、线程和游戏进度。发送自然语言会经过 Agent，而跳时间按钮直接执行 runtime；是否安排跨日事件因此依赖入口。

我此前做的设置/侧栏调整也仍在这个大文件中，并新增展示函数和 UI 测试入口。它解决布局，但没有解决职责混杂，后续应一起拆开。

需要的是一个简洁的会话模块：载入世界、提交行动、取玩家视图、存档/读档。Qt 或 Ren’Py 只调用同一个接口；生成工具不再由主窗口组织业务步骤。

### 2.7 模型调用的等待和成本缺少统一管理

普通成功回合通常至少一次规划和一次叙述；修复、协议降级、睡眠/跨日规划会追加请求。各处独立处理 400/422 降级和重试。Provider 虽解析 token usage，上层没有统一累计展示。

长设定按约 1,800 字节分段，每六段再摘要。静态估算：900 KiB 纯文本在不触发额外拆分、修复的理想情况下，单整理过程就约 512 次分类 + 86 次摘要；之后还有地图、需求、规则、开局和 NPC 生成。约六百次请求是代码路径估计，不是实际账单测量。

Qt 在 worker 中等待网络，有单请求超时，但没有贯穿整个任务的取消机制；析构函数会等待工作线程，关闭窗口可能等到长生成任务结束。模型失败不应让普通睡眠等确定性行为必须反复重新规划才能完成。

建议先有一个任务进度、取消、实际 token 计数和简单阶段保存；模型失败可暂时不生成新的气氛事件，核心动作仍遵循确定规则。

### 2.8 存档身份与迁移方式不利于编辑世界

生成世界的 ID 由世界观、地图和实际生成内容计算。它能区分内容快照，却把“这个世界是谁”和“这个版本具体是什么内容”混为一体。小改描述重新生成也会形成不同世界身份。

存档在同一个 v1 格式名下通过多组完整字段集合辨认历史版本。包括我添加的 encountered_npcs，也是在这套机制上再加一个兼容分支；这不是适合继续堆字段的长期方案。

建议采用稳定 world_id、显式 revision 和内容 hash。先保证新格式自己的存读档闭环；旧存档迁移不作为第一版主体的阻塞条件。

## 3. 冗余与不合适的实现方式

| 当前实现 | 问题 | 建议 |
|---|---|---|
| AgentAction 与 StoryChoice 重复结构，执行前再转换 | 两套行为入口和语义易分叉 | 把共同的前置/效果作为统一动作定义，剧情选项只是入口之一 |
| 同一行动类型在 enum、JSON 解析、JSON 导出、提示词和 runtime 分支重复声明 | 加一个动作要同步多处，长 if/else 不断增长 | 用小型类型化动作定义及集中分派；不用为了减少 if 再造复杂插件系统 |
| 保存、模型上下文、Qt 展示分别重新解释 StoryState 与物品名称 | 视图不一致、角色权限混入展示代码 | 会话模块输出一个玩家视图；存档保留自己的明确格式 |
| Schema、手写加载器、语义校验器、规则编译器、文档分别描述格式 | 并非全部都多余，但缺少统一契约来源，容易漂移 | 保留必要的语义校验，把结构契约集中；不要机械删除校验 |
| 多处复制模型 JSON 截取、修复和协议降级 | 错误行为与耗时难控制 | 统一一个生成请求帮助模块 |
| 整个 StoryState 多次复制，StoryDelta 同时保存 before/after，UI 又复制 package/state | 小世界可接受，大世界成本会放大 | 暂不做性能工程；先让快照责任集中，再根据真实规模决定是否改事件增量 |
| `swap_story_state` 手工列举成员 | 当前遗漏 player 的交换，现有动作未直接修改 player，因此不是本次已证实的建角丢失 bug；但新增字段容易漏 | 维护一处状态提交实现，验证真实改变的成员 |
| Python demo 使用另一套格式和运行循环 | 并不是可以直接替换现 C++ 的同功能后端 | 移入示例/归档，避免两条产品主线；仅迁移有用的经验 |
| 桌面构建找不到 Qt 会安静跳过；CI 没有显式装 Qt | CI 通过不能证明玩家程序通过 | 单独明确桌面构建目标，缺必要依赖就失败 |
| Windows 打包脚本默认写死 `E:\QT\6.10.1\mingw_64\bin` 且默认旧版本号 | 接手者难以复现发布 | 参数化或明确本地工具配置，保持一个可重复打包入口 |

这里更重要的是业务模型是否合适，不是追求最少文件或最少行数。Provider/Transport 的隔离、原子提交、加载前检查都有实际价值，值得保留。

## 4. 原作者已有世界设定生成工具吗？

**有，已经集成在项目里，不只是一个输入 JSON 的接口。**

入口：设置 → 世界与存档 → 填写／修改世界设定表 → 根据世界观生成探索世界包。

| 阶段 | 代码 | 产物 |
|---|---|---|
| 填表、导入文档、保存草稿 | `apps/talestate-desktop/world_brief_dialog.cpp` | `talestate.world-brief/v1` 草稿 |
| 分段整理原设定 | `src/agent/world_setting.cpp` | facts / rumors / secrets / rules / style 和 compact_brief |
| 生成地图 | `src/agent/world_map_generator.cpp` | 地点与路线草案 |
| 提取部分需求，生成规则、开局、物品、NPC | `src/agent/world_seed_generator.cpp` | WorldSeedDraft |
| 将白名单规则转成引擎动作 | `src/agent/world_spec.cpp` | variables、actions 和规则摘要 |
| 校验、导出、加载 | loader / validator 与桌面端 `generate_seed()` | `story.json`、`story.world-spec.json` |

`story.world-spec.json` 是可查看的中间规格，当前游玩加载的是 `story.json`。生成路径在桌面端；现 CLI 只有 validate / play，不是独立的世界创作工具。Python demo 也不是这套生成器。

局限：需求核对依据的是压缩到最多 3,500 字节的 brief，核对范围主要是属性名和“花费属性 A、增加属性 B”；它不能证明原文中全部约束被实现。生成的 JSON 结构合法，也不等于已经生成合理完整的游戏。

应保留“原文 → 需求 → 可编辑中间规格 → 编译 → 导出”的分层，把固定模板移走。长文原文和带来源需求清单应留在创作工程，摘要只服务于叙述与检索；不要求首版一次支持任意自然语言规则。

本次确认的是仓库内工具。公开 GitHub 账户的完整仓库列表获取遇到 TLS/页面读取失败，不能据此断言作者没有其他外部或私有工具。

## 5. Evennia 可行性

Evennia 能提供 Python 世界对象、房间/角色、持久化、命令、连接与管理设施；它是需要自行定义玩法的框架，不会自动提供符合本项目需求的 AI 剧情和规则系统。[官方介绍](https://www.evennia.com/docs/latest/Evennia-Introduction.html)、[Typeclasses](https://www.evennia.com/docs/latest/Components/Typeclasses.html)

对我们的价值：若确定多人共享持续世界，账号、连接、实体存储与后台管理可减少重造基础设施的工作。即使单人在本机也可以运行，但它的 Portal/Server 进程和服务器组织方式会给客户端分发、按玩家存档和暂停世界增加需要处理的工作。这是结合项目目标的工程判断，不是说 Evennia 技术上不能做单人。[Portal/Server 架构](https://www.evennia.com/docs/latest/Components/Portal-And-Server.html)

需要新做的仍包括：受限 AI 规划、玩家/NPC 知识、任务证据、生成世界导入、按回合推进的时间和剧情导演。阻塞式模型请求不能直接放在主命令执行中；它会影响其他玩家，需采用适合 Twisted 的异步处理或外部工作任务。[官方异步说明](https://www.evennia.com/docs/latest/Concepts/Async-Process.html)

它的 REST API 主要用于读写对象，默认创建/列表权限是 Builder 级别；这不是可直接给所有玩家用的“自由行动事务接口”。若 Ren’Py 接入，需要另做游戏会话接口，不能用通用对象 CRUD 绕过游戏规则。[REST API](https://www.evennia.com/docs/latest/Components/Web-API.html)

建议：目前作为多人候选。若后续采用，让 Evennia 成为唯一世界状态拥有者，迁移必要规则；不要让 C++ 和 Evennia 各保存一份背包再双向同步。

## 6. Ren’Py 作为前端可行性

可行，且对“单人优先、文字与人物演出”的方向比继续堆 Qt 表单更值得试验。Screen Language 能自定义角色栏、背包、输入、设置与对话界面，不要求把每个 AI 回合预写成 label。[界面系统](https://www.renpy.org/doc/html/screens.html)

可使用 JSON 会话接口接后端；官方 `renpy.fetch` 支持 HTTP(S) 和 JSON。调用位置很重要：文档指出在交互之外会让出界面，在 Action 等交互内部调用则可能阻塞显示。不能简单把长模型请求塞到按钮绘制或更新中。[网络请求](https://www.renpy.org/doc/html/fetch.html)

必须解决四个实际整合点：

1. **唯一状态拥有者。** Ren’Py 只保存展示所需数据或某个已提交快照。不能让它默认的回滚只撤掉界面变量，而后端物品和任务已经提交。首版可明确关闭动作回滚，仍支持显式存读档；以后再做完整历史回滚。[存读档与回滚](https://www.renpy.org/doc/html/save_load_rollback.html)
2. **一次动作只提交一次。** Screen 会被反复求值甚至预测执行；网络与世界提交必须在明确的用户动作处理中，不放在 screen 声明求值过程。[Screen 副作用说明](https://www.renpy.org/doc/html/screens.html)
3. **模型输出只作数据。** 不生成并执行 `.rpy` 或 Python 代码。显示文本时正确处理标签与插值，例如文本中的 `{}`、`[]`；官方支持引号转换与转义。[文本规则](https://www.renpy.org/doc/html/text.html)
4. **实际输入与素材体验。** 中文 IME、长输入、复制粘贴要在目标平台实测。可生成任意世界不代表自动拥有对应背景、立绘和表情；首版先用少量现成素材/占位图，不同步开发视觉素材生成平台。

Qt 中的世界设定大表单、地图编辑等创作工具不必全搬进 Ren’Py。玩家端和创作端可以分开。现有运行时没有网络会话服务，所以当前也不是换一个 Ren’Py 皮肤就能接通；需要先抽出会话模块与一个薄的传输适配。

C++ 保留方案可先用独立本地进程/接口隔离；直接做 Python 扩展也可行，但会增加平台、运行时版本和存档对象处理成本。Ren’Py 官方也说明非内置 Python 包不一定可直接工作，应做最小样例验证后再决定。[Python 支持](https://www.renpy.org/doc/html/python.html)

本次只完成源码与官方资料评估，没有安装 Evennia 或 Ren’Py、没有完成真实互联原型；“可行”指存在明确实现路径，不指现成兼容。

## 7. 路线取舍

| 路线 | 当前价值 | 主要成本 | 建议 |
|---|---|---|---|
| 现 C++ 会话模块 + Qt | 现成可运行，迁移最少 | 现有耦合和展示体验需继续处理 | 保留作对照，不继续向大主窗口加业务 |
| Ren’Py + 单一轻量会话运行时 | 契合单人叙事，适合人物/背景/音频表现 | 要接通会话、存档和输入；后端可以保留 C++ 或另行实现 | 首选小原型方向 |
| Evennia + 自定义玩家端 | 适合明确的持续多人世界 | 玩法仍需写，客户端打包和单人存档语义需另做 | 作为后续选择 |
| Ren’Py + Evennia | 可以组合表现与持续世界 | 仍要设计协议、身份、存档和时间；并非天然对接 | 多人需求确认后再评估 |
| Ren’Py + Evennia + 完整 C++ 双份世界 | 有技术实现路径 | 三套状态/存档与同步工作量 | 当前不选 |

不因为现有代码用了 C++ 就必须保留，也不因为主要调用模型就必须重写成 Python。没有性能剖析证据表明必须使用 C++；目前更直接的复杂度来自状态语义、生成流程和多次网络请求。先用同一小样例比较开发与接入成本再定后端语言。

## 8. 已对齐的最小下一步

用户已指定右侧 Codex 负责世界生成工具设计；双方已对齐“灯塔送药”样例：两个地点、玩家与守塔人、一件药品，先支持移动与交付。

生成侧：原文 → 带来源需求清单 → 可编辑世界定义 → compile → validate → export；后三步不依赖模型、Qt、Evennia 或 Ren’Py。格式先容纳样例实际需要的内容；复杂能力、知识系统、媒体配置可随后扩展。

运行侧：载入同一份定义 → 玩家输入/直接动作 → 原子交付改变所有者 → `delivered` 事件 → 任务完成 → 奖励一次 → 存档/读档。空动作不推进；没有交付时，模型的一句“已完成”不能完成任务。

先跑通这条链和一个 Ren’Py 玩家界面，再扩展闲聊记忆与更自由的行动。预约、复杂日程、多人、旧格式迁移和大量模板暂缓。此处是设计对齐，不表示新引擎或新生成器已实现。
